# پل سلامت (RxBridge) | پل ارتباط پزشک، بیمار و داروساز

**Status: v0.1.1 prototype — NOT FOR CLINICAL USE**

نمونه اولیه فارسی و راست‌چین برای نمایش گردش **پیش‌نویس نسخه → تأیید پزشک (شبیه‌سازی) → بررسی داروساز → ثبت تحویل آزمایشی**. تمامی اطلاعات ساختگی هستند.

## اجرای نمونه
بدون نصب وابستگی، فایل `index.html` را در مرورگر باز کنید. برای اجرای سرور محلی:
```bash
python3 -m http.server 8080
```
سپس آدرس `http://localhost:8080` را باز کنید.

## نام و هویت برنامه
- نام نمایشی فارسی برنامه در صفحه شروع، نوار بالایی و خروجی Android/iOS: **پل سلامت**.
- نام فنی و شناسه پروژه برای سازگاری مخزن و توسعه بین‌المللی: `RxBridge`.

## Supabase staging adapter (initial implementation)
- Added a provider-specific adapter behind the vendor-neutral contracts: `apps/mobile/lib/supabase_backend.dart`.
- Added composition root `backend_factory.dart`; Supabase initializes only when explicitly selected. Local SQLite is opened only in `localDemo` mode. Selecting an unimplemented Iranian backend fails closed rather than silently falling back.
- Added initial PostgreSQL schema and deny-by-default RLS policies in `infra/supabase/migrations/0001_staging_core.sql`.
- Added setup guide: `docs/SUPABASE_STAGING_SETUP.md`.
- Current adapter supports authentication, patient reads, lab-order reads/writes and glucose-reading reads/writes. Existing UI screens are **not yet wired** to these repositories, so cloud sync is not yet complete.
- Never put Supabase `service_role` keys in the mobile/web client. Use only project URL + anon/publishable key. Staging must contain synthetic data only.

## معماری قابل‌انتقال بین Supabase و سرور ایرانی
- از این مرحله، قراردادهای مستقل از ارائه‌دهنده در `apps/mobile/lib/backend_contracts.dart` تعریف شده‌اند؛ صفحات نباید مستقیماً به SDK یا API اختصاصی Supabase وابسته شوند.
- انتخاب محیط به‌صورت صریح و زمان بیلد است: `RXBRIDGE_BACKEND=localDemo|supabaseStaging|iranianServer`. تنظیمات عمومی موردنیاز هر محیط نیز اعتبارسنجی می‌شوند.
- راهبرد مهاجرت از Supabase به PostgreSQL و API میزبانی‌شده در ایران، شامل انتقال فایل‌ها، حفظ UUIDها، آزمون تطبیق داده، تغییر آدرس API و برنامه بازگشت در `docs/BACKEND_PORTABILITY_AND_MIGRATION.md` آمده است.
- این commit پایه معماری و قراردادها را فراهم می‌کند؛ اتصال واقعی صفحات به Repositoryها، آداپتور Supabase، آداپتور REST سرور ایرانی و سیاست‌های RLS هنوز اجرا نشده‌اند. بنابراین همگام‌سازی ابری فعال نیست.
- محیط آزمایشی فقط با داده ساختگی استفاده شود؛ کلید service-role و رمزهای سرور هرگز در برنامه موبایل قرار نگیرند.

## پایگاه داده محلی موقت نسخه تست
- برای تست موبایل، داده‌های **کاملاً ساختگی** برنامه پایش قند خون، درخواست‌های آزمایش و گزارش‌های آزمایشگاه در SQLite محلی ذخیره می‌شوند و پس از باز شدن مجدد برنامه بازیابی می‌گردند.
- دیتابیس `rxbridge_demo_only.db` رمزنگاری نشده و برای داده پزشکی واقعی مناسب نیست.
- دسترسی به داده از طریق قرارداد `CareSnapshotStorage` انجام می‌شود؛ کد صفحات به SQLite وابسته نیست.
- در نسخه نهایی، SQLite و وابستگی‌های آن باید **کاملاً حذف** و تنها API سرور دارای احراز هویت، رضایت و ممیزی جایگزین شود. هیچ داده نمایشی نباید به پرونده واقعی مهاجرت داده شود.
- برخی صفحات دیگر هنوز داده‌های ثابت نمایشی دارند و به پایگاه داده متصل نیستند.
- سند جزئیات و مسیر حذف: `docs/TEMPORARY_LOCAL_DATABASE.md`.

## پایش قند خون و خدمات آزمایشگاه (نمونه آزمایشی)
- نقش جدید **آزمایشگاه** در صفحه انتخاب نقش، با امکان مشاهده درخواست‌های نمونه و انتشار گزارش تفصیلی آزمایش.
- پزشک می‌تواند موعد آزمایش را از تقویم تعیین کند و برنامه تعداد نوبت‌های پایش قند خون در روز را با ساعت شروع تنظیم کند؛ این زمان‌ها تصمیم پزشک‌اند، نه توصیه برنامه.
- بیمار می‌تواند آزمایش‌های در انتظار و نتایج منتشرشده را مشاهده کند، عدد قند خون خانگی را با واحد mg/dL و زمان/شرایط اندازه‌گیری ثبت کند و در تاریخچه ببیند.
- در برنامه نمایشی، پزشک نمونه نیز نتایج قند ثبت‌شده را مشاهده می‌کند. این اشتراک صرفاً در حافظه همین فرایند است، **نه ارتباط واقعی بین دو دستگاه/کاربر**.
- پس از اقدام صریح بیمار و اخذ مجوز اعلان، برنامه سعی می‌کند یادآورهای روزانه محلی برای ساعت‌های تعیین‌شده ثبت کند؛ لغو یادآورها نیز وجود دارد. دقت و تحویل اعلان به تنظیمات و محدودیت‌های Android/iOS وابسته است و جایگزین هشدارهای درمانی یا سامانه نجات نیست.
- هیچ داده سلامت واقعی نباید وارد شود. ذخیره دائمی، همگام‌سازی بین دستگاه‌ها، احراز هویت، دسترسی مبتنی بر رضایت و گزارش آزمایشگاه دارای امضا و منبع معتبر هنوز پیاده‌سازی نشده است.
- پیاده‌سازی در `apps/mobile/lib/care_demo_store.dart`، `apps/mobile/lib/care_pages.dart` و `apps/mobile/lib/care_reminders.dart` است.

## بازطراحی رابط کاربری موبایل
- صفحه شروع و انتخاب محیط کاربری پزشک، بیمار، داروساز و مسئول بیمه
- داشبورد و ناوبری اختصاصی برای هر نقش با طراحی RTL، کارت‌های آماری، آیکن‌های مرتبط و انتقال نرم بین صفحات
- پنل بیمار: نمای پرونده سلامت، بخش محرمانه نمایشی، مدیریت رضایت نمونه، پروفایل پزشک و پیام‌رسانی نمایشی
- پنل پزشک: نمای بیماران، نسخه‌ها، پیام‌ها و پیگیری
- پنل داروخانه: نسخه‌های ورودی، موجودی و اعلام ناموجودی نمایشی
- پنل بیمه: آمار و گزارش‌های تجمیعی نمایشی
- تست‌های Widget برای انتخاب نقش و ناوبری نقش‌محور
- همه داده‌ها ساختگی و موقت‌اند؛ این رابط هنوز Backend، احراز هویت یا کنترل دسترسی واقعی ندارد.

## قابلیت‌های پیاده‌سازی‌شده
- فرم نسخه با شکل دارویی، مسیر تجویز سازگار با دسته انتخابی، مقدار/واحد هر نوبت، زمان‌بندی، مدت و دستور اضافی
- افزودن اقلام متعدد نسخه
- گزینه «سایر / مقدار سفارشی» برای شکل، مسیر، واحد و زمان‌بندی
- الزام علت انتخاب، مشاهده مجدد داده و تأیید صریح مقادیر سفارشی؛ هر تغییر پیش از تأیید نهایی نیازمند بازبینی و تأیید تازه است
- کنترل اولیه ورودی و جلوگیری از انجام عملیات با هشدارهای حل‌نشده
- گردش آزمایشی نسخه و نمایش سابقه اقدامات
- نگهداری داده‌های نمایشی فقط در حافظه جاری صفحه؛ با بارگذاری مجدد از بین می‌روند
- ابزار محاسبه حجم صرفاً ریاضی، نه تعیین دوز

## محدودیت‌های جدی
**این نسخه هیچ اتصال بیمه‌ای، پایگاه دارویی معتبر، احراز هویت حرفه‌ای، امضای دیجیتال، بررسی تداخل یا اعتبارسنجی بالینی ندارد.** برای هیچ بیمار واقعی، نسخه، محاسبه بالینی یا تحویل واقعی استفاده نشود. دکمه‌های «تأیید پزشک» و «بررسی داروساز» تنها شبیه‌سازی هستند؛ نقش‌ها در این نمونه احراز هویت نمی‌شوند. مقدار سفارشی حتی پس از تأیید کاربر به معنای ایمنی بالینی نیست. هیچ اطلاعات واقعی بیمار یا نسخه را وارد نکنید. بازخوانی صفحه داده‌های نمایشی را پاک می‌کند.

- برنامه نسخه‌بندی: v0.2 UI Flutter؛ v0.3 مدل و اعتبارسنجی؛ v0.4 API/Auth؛ v0.5 بانک دارو؛ v0.9 آزمون؛ v1.0 انتشار مشروط به ارزیابی ایمنی و مجوز.

## یادآور مصرف دارو (نقشه توسعه)
- یادآور بیمار باید از دستور معتبر نسخه استفاده کند و نام دارو، مقدار هر نوبت، مسیر مصرف، زمان‌بندی و بازه درمان را عیناً نمایش دهد.
- برنامه حق تعیین، حدس‌زدن، اصلاح یا دوبرابرکردن دوز را ندارد؛ در دستور ناقص یا متناقض، زمان‌بندی ساخته نمی‌شود و بیمار به پزشک/داروساز ارجاع داده می‌شود.
- بیمار می‌تواند وضعیت هر نوبت را به‌صورت «مصرف شد»، «فراموش شد»، «به توصیه درمانگر حذف شد» یا «یادآوری مجدد» ثبت کند؛ تاریخچه صرفاً گزارش خود بیمار است، نه اثبات مصرف.
- اعلان‌ها باید محرمانه، وابسته به مجوز دستگاه و قابل توقف باشند. این قابلیت هنوز پیاده‌سازی نشده و برای نسخه تولیدی به احراز هویت، همگام‌سازی امن، ممیزی و بازبینی ایمنی بالینی نیاز دارد.
- مشخصات کامل: `docs/PATIENT_RECORDS_PRIVACY_ARCHITECTURE.md`.

## نقشه راه تولیدی
- Backend: ASP.NET Core، پایگاه داده PostgreSQL و مهاجرت‌ها؛ ثبت رویداد ممیزی تغییرناپذیر
- Frontend: Next.js/TypeScript، طراحی RTL و دو زبانه
- احراز هویت، مجوزهای پزشک و داروساز، نقش‌های سازمانی، امضای دیجیتال
- بانک اطلاعاتی دارو با منبع و نسخه مشخص؛ محدودیت مسیر بر اساس **فرآورده مشخص** نه فقط شکل دارویی
- FHIR MedicationRequest/MedicationDispense، تطبیق با قوانین ایران و آداپتورهای مجاز بیمه
- موتور قواعد ایمنی مستقل با تست، بازبینی داروساز و هشدار غیرقابل‌دورزدن
- رمزنگاری، مجوز دسترسی داده، بکاپ، پایش و تست امنیت و بالینی
