# RxBridge backend portability and migration plan

## Decision
The application will use a vendor-neutral repository boundary. Supabase is the first hosted staging provider; a server hosted in Iran is a second implementation of the same application contracts. UI/domain code must not import Supabase SDK, PostgREST, PostgreSQL drivers, or provider-specific models.

## Provider topology
- Local prototype: disposable SQLite adapter; synthetic data only.
- Staging: Supabase Auth + PostgreSQL + Storage + Realtime, synthetic data only.
- Iran deployment: HTTPS API (FastAPI initially, replaceable) + PostgreSQL + object storage + WebSocket/SSE if required.

The provider is selected explicitly at build time using `RXBRIDGE_BACKEND=localDemo|supabaseStaging|iranianServer`. Staging and production credentials must never be embedded as service-role keys. Mobile receives only public/anonymous client keys; authorization is enforced by RLS/API.

## Stable application contracts
`apps/mobile/lib/backend_contracts.dart` defines AuthRepository, PatientRepository, CareRepository and RxBridgeBackend plus provider-neutral DTOs. Flutter pages should call these contracts through injected services. They must not call Supabase directly.

`apps/mobile/lib/backend_config.dart` validates the selected provider and required public configuration. This is a portability foundation, not a live Supabase connection yet.

## Data portability rules
1. Use UUID identifiers generated by the application/backend and preserve them across providers.
2. Store timestamps as UTC ISO-8601; store the patient's timezone separately (default Asia/Tehran only when explicitly selected).
3. Use stable snake_case field names and versioned migrations; never depend on provider-generated row IDs.
4. Keep binary files in object storage behind an ObjectStorage interface. Store only object keys and metadata in PostgreSQL.
5. Do not use Supabase-specific SQL features in domain logic. Keep provider-specific SQL, RLS policies and triggers inside `infra/supabase/`.
6. Avoid whole-database/snapshot replacement. Use resource-level create/update operations, idempotency keys and optimistic concurrency.
7. Maintain an OpenAPI contract for the Iranian API and contract tests that run against both adapters.
8. Record audit events server-side. Consent revocation must take effect on subsequent reads and downloads.
9. Keep clinical terminology and codes source/versioned; do not use free-form provider enums as cross-provider identifiers.

## Migration sequence: Supabase -> Iranian hosting
1. Freeze schema changes and create a migration release; pause writes briefly or enable a transactional outbox/CDC strategy.
2. Export PostgreSQL using provider-neutral schema and data formats; transfer object files separately with checksums.
3. Import schema and data into the Iranian PostgreSQL instance. Preserve UUIDs, timestamps, constraints and audit history.
4. Run row counts, foreign-key checks, checksum checks and domain-level reconciliation.
5. Deploy the Iranian API implementing the same repository contracts/OpenAPI behavior.
6. Run contract tests, permission tests (doctor/patient/pharmacy/lab/insurer), load tests and connectivity tests from Iranian mobile operators.
7. Switch API base URL/provider by a signed release or controlled remote configuration. Do not ship database credentials in the app.
8. Keep Supabase read-only for a defined rollback window. If rollback is needed, reconcile writes; never dual-write without an idempotent outbox.
9. After acceptance, revoke old keys, archive/export according to retention policy and delete the staging project only after verified backup and approval.

## Avoiding lock-in
- PostgreSQL is the canonical relational database at both providers.
- SQL migrations are version-controlled and provider-neutral where possible.
- Storage keys are opaque and portable; no public Supabase URLs are stored in business records.
- Authentication is isolated behind AuthRepository. If identities must move, use a planned password reset/invitation flow rather than assuming password hashes are exportable.
- Realtime is an optional transport; critical state changes are persisted and recoverable through normal API reads.

## Security and staging guardrails
- Synthetic records only. No real patient data in staging.
- Never expose service_role, database passwords, JWT signing secrets or server credentials to Flutter/web clients.
- Enforce least-privilege RLS/API checks and deny-by-default access.
- Separate Supabase projects and credentials for staging and production.
- Backups and restore drills are required; a free tier is not a production SLA.
- Validate connectivity from multiple Iranian ISPs before choosing the staging region.

## Current implementation status
The repository currently contains the provider-neutral interfaces and build-time environment selector. The Flutter UI has not yet been migrated to these interfaces; Supabase adapter, Iranian REST adapter, production RLS, object storage adapter, auth flow integration and migration tooling remain subsequent implementation tasks. Do not claim server sync is active yet.
